1. What CareWork Is (and why)

CareWork is a multi-tenant SaaS platform for the Australian disability and aged-care sector. It competes with Mable, HireUp, and LikeFamily — with two key differences:

  1. Registered-provider-grade compliance — we keep full legal responsibility for compliance (unlike Mable, which shifts liability to contractors).
  2. Wellness-integrated care — matching by shared interests and monitoring worker burnout, not just skills and availability.

Pilot phase: HelpHome (the existing NDIS provider) is tenant #1 — the first coordinator organisation using the platform. Other coordinators can join as additional tenants.

Why build it (the story):

  • HelpHome uses VisualCare as its operational backbone (rostering, compliance, Xero). Client portal costs extra and wasn't licensed.
  • Existing clients have no self-service way to book support — they call/email Tonia.
  • Workers have no way to flag burnout before they quit.
  • Competitors charge 17–33% platform fees. We charge 0% on the worker rate (subscription model).

3. The Business Model

  • New company owns the platform (CareWork) — same owners as HelpHome.
  • Multi-tenant — each coordinator organisation is a tenant. Data is siloed.
  • Revenue streams:
    • Subscription: clients pay premium tier (currently $19/mo, hidden during pilot)
    • Future: B2B placement fees from coordinators
    • Future: Stripe/Xero integration for real payments (post-pilot)
  • Workers keep 100% of their rate — no per-booking deduction.
  • Registered-provider path: HelpHome is unregistered today (claims via PlanCare). Registration expected next year enables direct NDIS/HCP claims.

4. The Roles

Four roles. Each sees only their own world.

4.1 Client

  • Sees: Dashboard (workers, filters, booking), Wellness check-in
  • Can: Browse independent workers, book shifts, log mood/goals/satisfaction
  • Cannot: See coordinator workers, see other clients' data, access admin pages
  • Demo login: jane.doe@client.com / test

4.2 Worker

Two sub-types:

Independent (marketplace contractor):

  • Sees: My Hub with one tab: CareWork Marketplace
  • Can: Accept/decline marketplace requests, submit wellbeing check-ins
  • Cannot: See roster shifts (they have no coordinator), access coordinator/admin

Coordinator (belongs to a coordinator org, e.g. HelpHome):

  • Sees: My Hub with HelpHome Roster tab (plus Marketplace if dual)
  • Can: Same as independent + see assigned shifts from their coordinator
  • Cannot: See other workers' data, access admin pages

Dual worker (both types):

  • Sees: Both tabs — CareWork Marketplace + HelpHome Roster
  • Demo login: sarah.johnson@helphome-worker.com / test

4.3 Coordinator

  • Sees: Coordinator Hub (roster of assigned workers with wellbeing status), Verification Queue
  • Can: Filter by wellbeing status, schedule welfare chats, verify/revoke worker documents, see client requests for their workers
  • Cannot: See other tenants' workers, access admin-only pages
  • Demo login: tonia@helphome.au / test

4.4 Admin (CareWork platform super-admin)

  • Sees: Everything — all tenants, all workers, all clients
  • Can: All coordinator actions + see all client requests across the platform, view platform KPIs/charts/alerts/activity
  • Cannot: Nothing restricted (top-level role)
  • Demo login: admin@carework.au / test

Why this specific combination:

  • Hono because the same code runs on Cloudflare Workers today and Azure tomorrow (only the adapter changes).
  • postgres driver instead of pg because pg doesn't work in Workers (no TCP).
  • Hyperdrive because Workers can't hold raw Postgres connections — Hyperdrive pools them.
  • Supabase because it's the closest free-tier to Azure Postgres we'll eventually migrate to — no code changes needed, just a new connection string.

6. The Architecture

┌─────────────────────────────────────────────────────────────┐ │ BROWSER (desktop / mobile) │ └──────────────────────────┬──────────────────────────────────┘ │ HTTPS ▼ ┌─────────────────────────────────────────────────────────────┐ │ CLOUDFLARE PAGES (helphome-app.pages.dev) │ │ ├── React SPA (compiled from src/frontend/) │ │ └── Pages Function (functions/api/[[path]].ts) │ │ → forwards /api/* to the Worker │ └──────────────────────────┬──────────────────────────────────┘ │ HTTPS (server-to-server) ▼ ┌─────────────────────────────────────────────────────────────┐ │ CLOUDFLARE WORKER (helphome-api.lifewealth.workers.dev) │ │ Hono API — all business logic │ │ ├── Auth middleware (x-user-id header) │ │ ├── Role guards (client/worker/coordinator/admin) │ │ └── 30+ routes │ └──────────────────────────┬──────────────────────────────────┘ │ Hyperdrive binding ▼ ┌─────────────────────────────────────────────────────────────┐ │ SUPABASE POSTGRES (Sydney, ap-southeast-2) │ │ 14 tables, multi-tenant via tenant_id │ └─────────────────────────────────────────────────────────────┘

Why the proxy layer exists:

  • Without it, the browser hits the Worker directly (cross-origin), requiring careful CORS on every request.
  • With it: browser sees only helphome-app.pages.dev; proxy forwards to the Worker with clean headers; Worker sees a plain server-to-server call.

Security boundary:

  • Browser never talks to Supabase directly.
  • Supabase password exists only in local .dev.vars and Cloudflare Worker secret.
  • All data access goes through the Worker (which enforces role guards).

Session model:

  • Login stores helphome_logged_in, helphome_role, helphome_user_id, helphome_worker_contexts in localStorage
  • Every page has session-expiry guard: fetch 401/404 → clears storage → navigates to /login

12. Deployment

12.1 Deploy the API (Cloudflare Worker)

npx wrangler deploy

→ updates helphome-api.lifewealth.workers.dev

Requires wrangler.toml with Hyperdrive binding:

name = "helphome-api"
main = "src/api/index.ts"
compatibility_date = "2025-09-01"
compatibility_flags = ["nodejs_compat"]

[vars]
ENVIRONMENT = "production"

[[hyperdrive]]
binding = "HYPERDRIVE"
id = "f9dfbabe72104e969a7caa16fdf75769"

[dev]
port = 8787

Requires the Worker secret DATABASE_URL (set once via npx wrangler secret put DATABASE_URL).

12.2 Deploy the Frontend (Cloudflare Pages)

npm run build
cp -r functions src/functions
npx wrangler pages deploy src/dist --project-name helphome-app --branch main

Why the cp -r: Pages looks for functions/ next to the deploy directory. We deploy from src/dist/ so functions must be at src/functions/. Permanent fix pending (change Vite outDir to root dist/).

12.3 Run migrations

npx drizzle-kit generate    # create migration file
npx drizzle-kit push        # apply to Supabase (dev only — always review before prod)

12.4 Deploy secrets

npx wrangler secret put DATABASE_URL    # paste Supabase connection string when prompted

12.5 What to do BEFORE every deploy

  1. Run both smoke suites locally (§13)
  2. Commit and push all changes
  3. Deploy API first, then Frontend
  4. Run both smoke suites against production
  5. If broken → rollback (§15)

15. Emergency Recovery

Worker broken → rollback

Cloudflare dashboard
→ Workers & Pages → helphome-api → Deployments
→ click previous working version → Rollback

Effective within 30 seconds.

Pages broken → rollback

Cloudflare dashboard
→ Workers & Pages → helphome-app → Deployments
→ click previous working version → Rollback

Supabase connection issues

  • Supabase performs periodic backups on the free tier. Exact cadence and restore UI depend on plan.
  • Check Supabase dashboard → Database → Backups.
  • Restore via Supabase dashboard → Database → Backups
  • If password leaked: rotate in Supabase → update .dev.vars and Worker secret

Local PGlite corrupted

NEVER use taskkill /F /IM node.exe — corrupts PGlite.

If corrupted:

# Stop backend with Ctrl+C
mv .data/pg .data/pg.corrupted
mkdir -p .data/pg
# restart backend — seeds fresh

Git rollback

git log --oneline -20         # find good commit hash
git revert <hash>             # safe undo (new commit)
git push origin feature/multitenant

Full local reset

# Stop both servers
rm -rf .data/pg && mkdir -p .data/pg
npx tsx -e "import { getDb } from './src/db/connection.ts'; getDb().then(() => { console.log('DB OK'); process.exit(0); })"
